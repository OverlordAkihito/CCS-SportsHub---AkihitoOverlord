# Context Index and Update Map

This folder is the project's durable cross-session memory. Keep it evidence-based and concise enough to recover quickly.

## Read order at session start

1. `SESSION_HANDOFF.md` — immediate resume point and next action.
2. `WORK_STATE.md` — status, blockers, and the last observed checks.
3. `PROJECT_OVERVIEW.md` — what the product is trying to accomplish.
4. `REQUIREMENTS.md` — requested behavior and current evidence-backed state.
5. `ARCHITECTURE.md` and `DECISIONS.md` — system structure and choices, especially before touching data or integrations.
6. `SECURITY_AND_PRIVACY.md` — mandatory constraints for sensitive flows.
7. `AUTO_STATE.md` — machine-generated repository/Git snapshot; useful for locating changes, never proof that behavior works.
8. `DEVELOPMENT_SEQUENCE.md` and `PROMPT_COMPLETENESS.md` — use when planning substantial feature work or constructing a task prompt.
9. `SESSION_LOG.md` — use when prior context or rationale matters; it is a concise history, not an exhaustive transcript.

## Which file owns which fact?

| Information | Canonical file | Update trigger |
|---|---|---|
| Immediate continuation steps | `SESSION_HANDOFF.md` | Every meaningful task ending or blocker change |
| Product purpose and scope boundaries | `PROJECT_OVERVIEW.md` | Product purpose/scope changes |
| Requested features, acceptance criteria, evidence/status | `REQUIREMENTS.md` | Requirement changes or verified implementation-state change |
| Actual stack, data flow, trusted boundaries, migrations | `ARCHITECTURE.md` | Architecture/codebase changes affecting those facts |
| Current active tasks, blockers, tests/results | `WORK_STATE.md` | Every meaningful work session |
| Durable decisions and rationale | `DECISIONS.md` | A decision is confirmed, changed, superseded, or rejected |
| Security/privacy invariants and findings | `SECURITY_AND_PRIVACY.md` | A security/privacy design, implementation, or risk changes |
| Meaningful historical events | `SESSION_LOG.md` | Meaningful completed work, decisions, incidents, or failed approaches |
| Git/worktree/structure snapshot | `AUTO_STATE.md` | Regenerated by `scripts/context_sync.py` |
| Milestone order and release checks | `DEVELOPMENT_SEQUENCE.md` | Dependency order/scope/release checklist changes |
| Prompt completeness method | `PROMPT_COMPLETENESS.md` | Prompting standards change |

## Evidence and conflict rules

- A requirement describes what the product should do. It does not establish what code currently does.
- An audit statement should point to repository paths/symbols or an observed check where feasible.
- A test passing supports only the behavior it actually exercised; do not inflate test scope.
- Record an architecture proposal as proposed until selected and supported by evidence.
- Record unknowns plainly. Do not turn uncertainty into a confident default to make the files look complete.
- If a context note contradicts the repository, inspect and update the note with a short rationale. Do not preserve stale claims solely for continuity.
- Keep context free of credentials, tokens, secrets, private records, and unnecessary personal data.

## Keep it efficient

Do not paste all context files into every task prompt. Read the focused subset and follow cross-references. Preserve stable decisions and current state; avoid copying entire chat transcripts or repeated explanations. Keep the handoff and work state short enough that the next agent can identify the next action quickly.
